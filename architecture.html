Stage 1 — Game Engine (Client-side)

The browser game engine is a pure TypeScript module with no external game library. Each layer has a single responsibility.

GameEngine owns loop, state, input, renderer │ ├── InputHandler keyboard keys → MovementVector │ ├── tick() pure fn: movePlayer + detectNearbyZone │ │ │ ├── movePlayer() apply velocity, clamp to world bounds │ └── detectNearbyZone() proximity check vs interaction zones │ ├── computeCamera() pure fn: centre viewport, clamp to world │ └── Renderer Canvas 2D: background, stars, zones, player, HUD

Why pure functions for physics?

movePlayer, computeCamera, and detectNearbyZone take state in and return new state out — no DOM, no Canvas, no React. This means they run in a Node.js test environment with zero setup. In Stage 2, the same functions will accept server-authoritative positions instead of locally computed ones, without any change to the renderer.

DPR-aware canvas sizing

On Retina displays devicePixelRatio is 2 or 3 — a canvas at 1:1 looks blurry. The renderer sets canvas.width = logicalW × dpr and calls ctx.setTransform(dpr, 0, 0, dpr, 0, 0) at the start of each frame. Game logic always works in logical pixels; the DPR scaling is invisible to physics and camera code.

Procedural star field

Stars are not stored in memory. The renderer uses a deterministic hash sin(tx·127 + ty·311 + offset·74) × 43758 per tile coordinate to decide whether a tile contains a star and where. The same tile always produces the same star, so the field is visually consistent as the camera moves — but there is no array to allocate or serialise.

Diagonal movement normalisation

Without normalisation, holding W+D moves at speed × √2 ≈ 1.41×, which feels wrong. The input handler sums the direction vectors from all held keys, then divides by the magnitude when both axes are non-zero. Result: every direction moves at the same speed.

Key Architectural Principle: Server Authority

Client never sends

  • Final player position
  • Light balance
  • Meteor ownership claims
  • Reward values
  • Star creation
  • Moderation decisions

Client only sends intents

// direction only — not coordinates
{ direction: "right", sequence: 42 }

// content only — not status
{ category: "hope", content: "…" }

// choice only — not outcome
{ meteorId: "…", responseType: "…" }

Typed Protocol Contract

The @afterlight/protocol package defines the complete Socket.IO event interface. Both the server and client are parameterised with the same types, giving compile-time safety on every event.

// packages/protocol/src/index.ts

export interface ClientToServerEvents {
  'player:join':        (payload: PlayerJoinPayload) => void;
  'player:move':        (payload: PlayerMovePayload) => void;
  'meteor:create':      (payload: MeteorCreatePayload) => void;
  'meteor:acknowledge': (payload: MeteorAcknowledgePayload) => void;
}

export interface ServerToClientEvents {
  'world:snapshot':       (payload: WorldSnapshotPayload) => void;
  'player:moved':         (payload: PlayerMovedPayload) => void;
  'meteor:created':       (payload: MeteorCreatedPayload) => void;
  'star:created':         (payload: StarCreatedPayload) => void;
  'light:earned':         (payload: LightEarnedPayload) => void;
  'notification:heard':   (payload: NotificationHeardPayload) => void;
}

Adding a new event without updating both interfaces causes a TypeScript compile error before it reaches runtime.

Meteor Lifecycle

DRAFT ↓ player submits content SAFETY_CHECK ↓ passes classification PUBLISHED ← enters the shared world, visible to all players ↓ player approaches ENCOUNTERED ↓ player selects a response ACKNOWLEDGED ← writer receives private "Someone heard you" ↓ simultaneously STAR ← permanent entry in the sky; helper receives +1 Light SENSITIVE ← held for human review (never public until cleared) HIGH_RISK ← never published; crisis support flow shown to writer

Database Schema

users             id, created_at, last_seen_at, status
players           id, user_id, zone_id, position_x, position_y
meteors           id, player_id, category, content, status, safety_status, position
resonances        id, meteor_id, player_id, response_type
                  -- UNIQUE(meteor_id, player_id) prevents duplicate acks
stars             id, meteor_id, position_x, position_y
light_transactions id, player_id, amount, reason, reference_id
                  -- append-only ledger; balance = SUM(amount)
items             id, item_type, name, metadata
player_items      id, player_id, item_id, quantity

Light is stored as transactions (not a mutable balance column) for auditability and correctness. You can always recalculate a player's balance from the ledger.

Safety Pipeline

User content ↓ Length / format validation ← cheap; catches obvious bad input ↓ Safety classification ← context-aware; NOT just keyword matching ↓ ┌────────────────┬─────────────────┬──────────────────────┐ │ SAFE │ SENSITIVE │ HIGH_RISK │ │ │ │ │ │ Publish to │ Hold for human │ Do not publish. │ │ shared world │ review │ Show calm support │ │ │ │ resources. │ └────────────────┴─────────────────┴──────────────────────┘

A keyword blacklist alone is not sufficient. "I could die laughing" should not trigger a crisis flow. Indirect hopelessness that uses no flagged words should. Context-aware classification is required before public launch.

Scaling Path

MVP (Stage 0–3) Browser → Game Server → PostgreSQL Stage 9+: when profiling demands it Browser → Gateway → World Server(s) │ Redis pub/sub ← session presence, cross-server events │ PostgreSQL ← durable state unchanged

Redis is not in MVP. A single Node.js process handles thousands of concurrent WebSocket connections. Add Redis when measured requirements justify it, not before.

Architecture Decisions (ADRs)

ADR-001 Separate web client and game server

Decision: Next.js for the web app; a separate Node.js process for the game server.

Why: Different performance characteristics, lifecycle, and scaling concerns. The game simulation can't share GC settings or deployment topology with an SSR web app.

ADR-002 Server-authoritative world state

Decision: The server owns all gameplay state. Clients send intents; the server validates and broadcasts results.

Why: Prevents cheating, ensures consistency across all clients, maintains the integrity of emotional interactions (a faked acknowledgment would corrupt the "Someone heard you" moment).

ADR-003 Socket.IO for realtime transport

Decision: Socket.IO over raw WebSocket for MVP.

Why: Built-in reconnection (critical for a wellbeing game where sessions are emotionally significant), typed event patterns, rooms/namespaces, fast development. Raw WebSocket re-evaluable if benchmarks show overhead.

ADR-004 PostgreSQL for durable state

Decision: PostgreSQL with relational constraints and transactions.

Why: The data model is inherently relational. UNIQUE constraints enforce one-resonance-per-player at the database level. Transactions make the acknowledge → star → Light sequence atomic.

ADR-005 No Redis in MVP

Decision: Defer Redis until profiling shows the need.

Why: Premature complexity. A single Node.js server handles the initial world. Redis adds a failure point, operational cost, and consistency surface area without solving a current problem.

ADR-006 2D before 3D

Decision: 2D Canvas rendering for MVP.

Why: The differentiator is the social and realtime mechanic, not visual fidelity. 3D asset production would consume development time without validating the core idea.

ADR-007 No free-form player chat

Decision: Predefined responses only — no arbitrary text between players.

Why: Eliminates the moderation surface for harassment, manipulation, grooming, and misinformation while keeping the acknowledgment mechanic fully intact.

ADR-008 One acknowledgment transforms a meteor

Decision: The first valid acknowledgment transforms the meteor to a star.

Why: Avoids popularity-based emotional valuation. Additional resonances are recorded but don't change the writer's star or their "Someone heard you" moment.

ADR-009 Light is cosmetic-only

Decision: Light unlocks garden cosmetics only — not gameplay power or public status.

Why: The game should not quantify mental health or create competition over empathy. A visible "empathy score" would corrupt the social dynamic the game is trying to create.
